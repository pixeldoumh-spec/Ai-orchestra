# V6.6.1 — Runtime Integrity & Reliability

V6.6.1 hardens the V6.6 durable background execution plane against duplicate dispatch, stale workers and lease-state corruption.

## Runtime invariants

- A task in `running` state must carry a lease owner and lease expiry.
- Each lease acquisition increments a monotonic `lease_generation` fencing token.
- Heartbeats are accepted only from the current worker and lease generation.
- A stale worker cannot overwrite a newer worker's task state.
- A worker that exits while a task is still `running` safely requeues it instead of clearing the lease and leaving an orphaned running task.

## Dispatch safety

Cron recovery remains tenant-scoped and uses two independent guards:

1. An application-side eligibility check prevents obvious duplicate redrives.
2. PostgreSQL `reserve_task_dispatch` serializes the final decision under a per-task advisory lock.

A running task is redriven only when its lease is expired or absent **and** its heartbeat is stale. A recent heartbeat therefore protects a slow-but-live worker from duplicate execution.

Dispatch reservations have a short cooldown window. If queue publication fails after reservation, the task remains eligible for a later retry after the cooldown rather than being continuously re-enqueued.

## Queue failure visibility

Queue deliveries that reach the configured retry boundary are recorded in `background_dead_letters`. Only bounded execution metadata and a payload hash are stored; prompts, outputs and secrets are not persisted.

The existing Cloudflare Queue dead-letter destination remains authoritative for message retention/recovery, while the database record provides tenant-scoped operational visibility.

## Worker telemetry

Each queue delivery continues to create a durable `background_worker_runs` record. V6.6.1 ensures a worker-run record is closed exactly once for normal completion, skip, lease loss or retryable failure.

## Recovery settings

Production defaults:

- `TASK_LEASE_SECONDS=600`
- `TASK_STALE_HEARTBEAT_SECONDS=120`
- `TASK_DISPATCH_COOLDOWN_SECONDS=45`
- `TASK_REQUEUE_DELAY_SECONDS=1`
- `TASK_QUEUE_MAX_RETRIES=5`

These values are intentionally bounded and may be overridden by runtime configuration within the database-function safety ranges.

## Scope

V6.6.1 is a reliability release. It does not change the model provider contract, tenant RBAC, connector permissions, billing policy or agent-network authorization model.


## Step-level convergence

Task recovery is also fenced at the step level. Each running step records the worker identity and task lease generation that started its current execution attempt. When a task is reclaimed under a newer lease generation, running steps from the older or unknown generation are atomically requeued before the DAG is evaluated again. This prevents a stale `running` step from blocking the workflow indefinitely after a worker crash or deployment boundary.

The step recovery path never fabricates a result. It schedules the step for a fresh execution under the new task lease, allowing the normal model/tool/evidence/verification pipeline to produce the result again.


## Stale active-lease takeover

A lease can remain nominally active while its worker has stopped heartbeating. V6.6.1 therefore adds a conservative **5-minute stale-lease takeover** before normal claim processing. It applies only when the task is still marked `running`, the lease has not yet expired, and its heartbeat is at least 5 minutes old.

The takeover clears only that stale owner lease and requeues the task. The existing PostgreSQL lease-generation fence then assigns a new generation, and step-level recovery requeues any `running` steps that belonged to the older or unknown generation.

A fresh heartbeat never qualifies for forced takeover. The threshold is configurable through `TASK_STALE_LEASE_TAKEOVER_SECONDS` and is bounded to a minimum of 5 minutes in application code.
