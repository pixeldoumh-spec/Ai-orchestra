# V6.6 — Production Operations

V6.6 moves orchestration execution from browser-coupled requests to a durable Cloudflare Queue.

## Execution lifecycle

1. The authenticated task start endpoint returns 202 Accepted after placing a tenant-scoped dispatch message on ai-orchestra-tasks-v66.
2. The same production Worker consumes the queue in a background event handler.
3. Queue retries are bounded and failed deliveries go to ai-orchestra-tasks-v66-dlq.
4. A one-minute scheduled handler re-drives due or lease-expired tasks that have not been dispatched recently.
5. Task leases and heartbeat fields are updated in Supabase so duplicate workers cannot claim the same task concurrently.
6. task_events is the durable event stream; /api/tasks/:id/stream exposes it as authenticated SSE with Last-Event-ID replay and refreshed task snapshots.

## Model resilience

The model adapter records provider/model provenance and can fail over from the primary model to a configured secondary model. Production configuration uses Workers AI @cf/openai/gpt-oss-20b as primary and @cf/zai-org/glm-4.7-flash as the bounded fallback. Fallback activation is limited to transient/capacity/quota/authentication-style failures.

The Cloudflare adapter keeps Responses-style execution for the primary model and uses the model-compatible chat-completions contract for GLM fallback, including function calling and disabled reasoning for predictable output budgets.

## Observability and usage

task_execution_metrics stores append-only model execution telemetry without prompts, outputs, or secrets. It captures latency, token usage, monetary usage, Workers AI resource usage, fallback provenance, and bounded error classifications.

background_worker_runs records queue/cron execution attempts.

get_operations_dashboard provides tenant-scoped aggregates for model volume, success/failure, fallback rate, p50/p95 latency, tokens, Workers AI neurons, worker p95 latency, task outcomes, daily rollups, and provider/model breakdowns.

The enterprise control plane surfaces these metrics under Production Operations.

## Tenant isolation

All operations metrics and task dispatch state remain organization-scoped. Browser roles can read their tenant's metrics but cannot insert/update/delete execution telemetry. Queue consumers use the existing service-role-backed orchestration repository and preserve the existing task lease, policy, connector, and knowledge boundaries.

## Runtime caveat

V6.6 uses the existing OpenNext Worker as a custom Worker entrypoint so Cloudflare fetch, Queue consumer, and scheduled handlers share one deployment. This avoids a second Worker and avoids copying Supabase or AI secrets into another runtime.
